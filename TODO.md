- Source repo: `vekrona-theme` reloads running Ghostty windows (`reload_ghostty` in `bin/vekrona-theme`, a D-Bus `reload-config` action), and Ghostty answers with its "Reloaded the configuration" toast in every open terminal, for real users too. Adding `app-notifications = no-config-reload` to `config/ghostty/config` suppresses it (it has no `app-notifications` line today). The capture scripts work around it by passing `--app-notifications=no-config-reload` to every Ghostty window (`ghostty_window` in `capture/remote.sh`).
- Source repo: `vekrona-theme` overwrites the active theme file in place (`cp "$json" "$ACTIVE_THEME_FILE"`). DMS watches that file, and when it reads between the truncate and the write, `Theme.qml` `parseAndLoadTheme` shows a red "Invalid JSON format: JSON.parse: Parse error" toast. Seen in the theme-cycle recording; it is intermittent (one of two recordings). Writing to a temp file and `mv`-ing it over the target would avoid it. `record_theme_cycle` now detects the toast and records again.
- Source repo: stopping `tailscale-systray.service` (`systemctl --user stop`) makes the process exit with status 1, so systemd marks the unit failed and `vekrona-error` records "tailscale-systray.service failed" with a badge and a toast. `SuccessExitStatus=1` in `config/systemd-user/tailscale-systray.service` would make a clean stop clean. Reproduced twice in the guest on 2026-10-01.
- Source repo: the installer's stage `40-system` sets the Tailscale operator with `tailscale set --operator=$USER`, and stage `70-verify` asserts it. On a guest that has never logged in to Tailscale (no profile), `tailscaled` starts with default prefs after a reboot or daemon restart, so the operator is empty again and `./install.sh 70` fails on that assertion; the tray service also exits with "No permission to manage Tailscale". Observed on 2026-10-01: operator set by the install, guest rebooted, pref empty with `LoggedOut: true`. The workaround for a capture run is `sudo tailscale set --operator=<user>` in the guest (lasts until the next daemon restart). Options for the source repo: re-apply the operator when `tailscaled` starts (for example a systemd drop-in with an `ExecStartPost`), or have stage 70 skip the operator assertion while Tailscale is logged out. The vekrona source repo has a fix on the `integration` branch (commit `a63e3c0`) that turns stage 70's operator check into a warning naming the remedy while the node is logged out and keeps it an assertion once logged in; it is not on `main` yet as of 2026-10-01, and until the capture VM's checkout includes it, the workaround in this entry is still needed before a reshoot. The fix does not cover `tailscale-systray`, which still exits with "No permission to manage Tailscale" on a logged-out node; with the fix, verify on a logged-out guest will end with a warning rather than all-ok, so the terminal still shows a warn line, whereas setting the operator before a reshoot keeps the output clean.
